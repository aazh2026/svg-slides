# 页面版型与分析方法

| 版型 | 适合 | 不适合 |
|---|---|---|
| architecture | 分层架构、控制面/数据面、模块依赖 | 无层次的要点列表 |
| process | 有明确顺序的生命周期、数据加工、变更流水线 | 并行或无顺序的能力目录 |
| matrix | 选型、因果分析、能力映射、技术趋势 | 复杂反馈或调用时序 |
| compare | 2–3 个方案、有对称维度的新旧机制 | 需要证明量化差异却无数据 |
| cards | 2–6 个并列要点、必要条件、风险 | 复杂依赖、数据流 |
| custom | 网络拓扑、状态机、时序图、复杂分支、血缘、双平面 | 简单表格或列表 |

## 先选图形结构

先用一句话写出读者看完主图应能回答的问题，再画关键节点和连接的草图。表中的图形结构可用自定义 SVG 实现。内置版型能完整表达关系时可直接使用。

| 读者要看懂的关系 | 图形结构 | 画出什么 |
|---|---|---|
| 权限或职责如何继承 | 层级树 | 父子节点、继承方向、平级隔离 |
| 多个主体如何覆盖同一对象 | 汇聚拓扑 | 各自路径与边界、共享目标 |
| 一个事件改变哪些记录或权限 | 前后状态图 | 相同实体在变更前后的状态、触发点、保留与移除 |
| 一组输入如何被筛选 | 集合图或分流图 | 输入、判定条件、通过及过滤结果 |
| 多种机制怎么选 | 对比矩阵 | 共同比较维度、使用条件、关键代价 |
| 遇到异常先查什么 | 决策树 | 判断问题、不同答案的分支、终点或复测 |
| 工作分阶段如何交付 | 流程或时间线 | 阶段顺序、交接物、验收点；有不同参与方交接时采用泳道 |

## 整套版式验收

按页码并排看缩略图，重点比较主图区域。检查节点如何组织、连线如何走、读者先看哪里，以及主图与解读区如何分配空间。只改变文字、颜色、卡片数量或局部合并，仍视为同一构图。

对于同时包含多类技术关系的报告，同一构图覆盖过半页面，或连续三页使用同一构图时，回查页面计划并改画关系不同的页面。若多页必须使用共同维度来横向比较，或延续同一机制以方便跟读，在 QA 中记录复用理由。按实际内容选用结构，页眉、页脚和颜色可保持统一。

## 技术文档拆解
1. 先找技术问题与设计目标，抽取名词与关系，而不是按原文章节机械分页。
2. 画官方可证实的机制：组件/主体、输入/输出、执行位置、信息方向、关键状态、治理控制点。
3. 对每个机制解释为什么、解决了什么、代价和边界；如果缺少信息，写待验证而非自行补齐。
4. 在企业 IT/目标业务语境下给出独立建议。建议可以借鉴公开机制，但不得声称产品已实现。
5. 架构页优先主图，将相关解读放在侧栏或图下。若箭头没有真实方向或顺序，使用分组框或无向关联。控制流与数据流在图注中区分；反馈箭头避免穿过文本。

## 密度策略
架构 2–5 层，每层 1–4 个节点；流程 2–6 阶段；矩阵 2–6 列、通常 4–10 行；对比 2–3 列、3–6 个维度；卡片 2–6 张。脚本按内容计算换行与容量，超限报错。复杂拓扑不应被这些默认数量限制，可自定义 SVG 或拆页。

## 文字说明密度

- 按页规划。旧版 2–4 个解释块以每块 1 条有效说明换算。重画时可按同一口径实测旧页；新做时按原规划口径，简明机制用 2 条作基线，含多分支或重要例外用 3–4 条。新版目标为基线的 2 倍，通常是 4–8 条。适用于解释机制、比较方案或指导实施的核心内容页。
- 一条有效说明须回答一个独立问题，并能回溯到证据或明确标注的推导、建议。可补充授权或执行条件、输入与结果、顺序、失败路径、适用范围、例外、权衡或验证方法。节点名、箭头短标签、表头、来源标识、底部结论及改写后的重复观点均不计数。
- 说明可以分布在节点旁的注释、矩阵的约束列、图下例外区或侧栏。按读者阅读路径就近放置，同类说明可以合在同一版面区域。继续遵守原有文字字号和图形结构。篇幅不足时先压缩措辞、调整图文分区，再考虑拆页。
- 来源不足时在 QA 记录可证实条数及缺口。静态脚本只校验 SVG，说明是否独立、是否有依据由交付者逐页核对。

## 内容标题示例
- 差：机制对标：对标机制，不做产品功能排名。
- 好：元数据 Core 保持权威，独立运行时按需同步（仅在证据支持时）。
- 差：构建全链路可信智能化底座。
- 好：异步动作受理后，仍需验证最终业务状态。

## 主图计数规则

- 适用于以解释技术机制为主要目的的页面，例如架构、授权关系、数据流和状态变化。计数范围只包含主图，排除页眉页脚、标题、来源、旁注和底部结论。
- 可见的 `rect`、`line`、`path`、`polygon`、`circle`、`ellipse`、`polyline` 和 `text` 在承载节点、分区、连接、方向、状态或标签时各计 1 个。连线和表示方向的箭头可分别计数，同一文本的 `tspan` 和外层 `g` 不增加计数。
- 排除背景、装饰、重复形状、空白表格单元格和人为拆分的线段。达到 40 个以后，仍需能沿主图读出谁对哪个对象执行什么操作、在何种条件下生效，以及结果或例外。
- 优先用贯穿同一业务场景的主体、记录、触发条件、分支和结果增加信息量。来源不足以支撑 40 个有效元素时，在 QA 记录实测计数和证据限制。该项由交付者核验，现有静态验证脚本不自动判定元素是否承载信息。
